Dense Layer

make_loaders() hands you a dict of seventeen tensors. No neural network takes it unchanged — and the reason is not the Linear layer. Here is what comes out, the five rules that stand between it and a trunk, and the arithmetic behind each one.

What actually comes out

Not a tensor. A dict, from collate(), holding three ragged groups padded to the longest row in that batch, four fixed-width tensors, and two lists of strings. Shapes below are one real batch at batch_size=256.

S, R and E are not constants. Each is the longest row in that batch. Across the training split the true lengths run: skills 4–16 (mean 9.1), requirements 3–7 (mean 4.9), employers 0–5 (mean 2.0). At batch 256 you almost always hit the ceiling and see (16, 7, 5) every time; at batch 8, S swings between 11 and 16 from one batch to the next.

So can I feed it to my network?

No — not its contents

Nothing in the dict can go into a layer as it stands. Two of the three groups are integer indices, and all three have an axis whose width changes between batches.

Yes — the dict itself

forward(batch) takes the whole dict. The conversions happen inside it: embed the ids, pool the ragged axes under their masks, concatenate.

The five rules

Why the batch is shaped the way it is

Each rule is a constraint the data imposes, the arithmetic that makes it a constraint, and what satisfying it costs.

RULE 1

An id is not a quantity

A dense layer computes z = Wx + b. It is affine in every component of x. Put a skill id in one of those components and you have asserted something false about skills.

z(s) = w·s + b a skill id fed as a number
∂z/∂s = w constant — one slope for all 76 skills
z(44) − z(43) = z(2) − z(1) adjacent ids must differ by the same amount
z(44) = 2·z(22) − b the 44th skill is "twice" the 22nd

The ids are alphabetical. AWS is 1 and Airflow is 2 because of how sorted() ordered them, so the model would be fitting a slope through an accident of the alphabet. An embedding replaces the slope with a lookup:

es = E⊤ onehot(s) row s of the table, E ∈ ℝ77×d
∂es/∂Es = I every skill gets d free parameters

That is d numbers per skill with no imposed order, instead of one shared slope. Row 0 is reserved in every vocabulary for padding, missing and unseen-at-test, so every table is built with padding_idx=0 — which also makes row 0 the zero vector, and that matters in Rule 4.

RULE 2

A layer has a fixed fan-in; the data does not

W ∈ ℝout×in is allocated once. The product Wx is defined only for x ∈ ℝin. Our S changes between batches, so there is no in to allocate.

batch 0: S=13 batch 3: S=15 batch 1: S=16 batch 4: S=12 batch 2: S=11 batch 5: S=16

Padding to a global maximum would fix the shape and break Rule 4 instead. The axis has to be reduced away, not filled in.

RULE 3

Skills are a set, so the reduction must be order-blind

Nothing in a CV makes Python come before AWS. The order in the tensor is whatever order the JSON happened to list. So for any permutation π the model must satisfy:

f(x1, …, xn) = f(xπ(1), …, xπ(n)) permutation invariance
f(X) = ρ( Σi φ(xi) ) Deep Sets: every such f has this form

Sum, mean and max satisfy it. An RNN does not — it would learn that the first-listed skill matters more, which is an artefact of serialisation. A Transformer satisfies it only with positional encoding removed. φ is the embedding; ρ is the trunk.

RULE 4

An unmasked mean makes the batch a feature

This is the one that does not raise an error. Let ni be row i's true length and L = maxk nk the padded width of the batch. Because padding_idx=0 makes the padded vectors exactly zero, the sum is already correct — only the divisor is wrong.

m̃i = (1/L) Σj=1L vij the naive mean, dividing by the padded width
= (1/L) Σj=1ni vij padded terms are zero, so they drop out
= (ni/L) · mi the true mean, scaled by a factor it did not choose

And L is a maximum over the batch — over other people's CVs. So the representation of one candidate depends on who else was sampled alongside them. Verified on a real batch, where ni/L matches the ratio of the two means to four decimals:

row 0: n= 7 L=13 n/L = 0.5385 naive/masked = 0.5385 row 1: n=11 L=13 n/L = 0.8462 naive/masked = 0.8462 row 2: n= 5 L=13 n/L = 0.3846 naive/masked = 0.3846 row 3: n= 6 L=13 n/L = 0.4615 naive/masked = 0.4615
mi = ( Σj maskij · vij ) / ( Σj maskij ) divide by the true length; clamp ≥ 1 for an empty row

Employers can legitimately be empty — 7,244 of the 94,848 training pairs involve a candidate with no employment history at all. That row's mask sums to zero, so the clamp is load-bearing, not defensive.

RULE 5

Pooling destroys the one thing the stack score needs

Mean pooling is not injective. Different sets collapse to the same vector, so |held ∩ wanted| — the whole question the stack section asks — cannot in general be recovered from the two pooled vectors:

mean(e1, e2) = (0.5, 0.5) two skills the candidate holds
mean(e3, e4) = (0.5, 0.5) two entirely different skills
|{1,2} ∩ {1,2}| = 2,  |{1,2} ∩ {3,4}| = 0 same input to the trunk, opposite truth

This is why required_skill_candidate_years exists. It is the years the candidate holds in each required skill, aligned index by index to the requirement list — a lookup, not a score, and the only field in the batch that looks derived. Column j means the same requirement across ids, min_years, weights and that lookup, so yearsj − min_yearsj is a signed surplus per requirement.

Measured  Without it, the stack head sat at 9.50 MAE. With it, 3.84. Nothing else changed.

It is not the Linear layer's fault

Swapping the architecture does not remove the work. Rule 1 and Rule 2 bind every family — an attention block still needs float vectors per token, and still has to produce one fixed-size output for four regression heads.

Architecture Takes raw ids? Takes a ragged axis? Still needs a reduction? Order-blind?
nn.Linear No No Yes n/a
nn.Conv1d No Yes Yes No
nn.LSTM / GRU No Yes Yes No
Transformer No Yes Yes If unpositioned
Deep Sets / pooling No Yes Is the reduction Yes

Every row needs an embedding table, and every row needs the ragged axis gone before the heads. What changes is only the middle step — mean pooling is the cheap reduction; attention over the requirement list is the one worth trying, because it keeps a single unmet must-have visible instead of averaging it away.

What is an input, and what is not

Four keys ride in the batch without ever reaching a layer. Two of them would be leakage.

KeyRoleWhy
scalarsInput Already standardised — the only key that is model-ready as it stands
*_ids, categoricalInput After an embedding lookup
*_years, weights, min_yearsInput As multiplicative weights on the embeddings
*_maskNot an input An instruction to the pooling, not a feature
job_weightsNot an input Combines the four outputs after the model
targetNot an input The label
job_id, candidate_idNot an input Strings, for grouping a pool. Feeding them is memorisation

One more rule that is not about shape: no feature may be computed from scoring_rules.py. Coverage ratios and domain-similarity coefficients are the answer the labels were generated from, not the input.

The whole path

Where this stands

The loader is built and tested. make_loaders() returns 60,389 training rows, 3,587 validation and 10,158 test, split on both postings and candidates. The model and the two loops are placeholders — every function raises NotImplementedError, and the numbered rules above are what they have to satisfy when they are filled in.
